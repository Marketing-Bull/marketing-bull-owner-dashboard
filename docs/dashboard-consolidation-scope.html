02 The core finding

The owner dashboard is a read-only viewer. What you are asking for is a system of record. That is the whole scope in one sentence, and almost every line item below follows from it.

Concretely: today "Clients" and "Projects" are not entities. They are ClickUp tasks pulled from two hardcoded list IDs and rendered as chips — the type is { id, title, subtitle, status, href }, with no client→project relationship, no rates, no contacts, and no way to create one. The only thing the app owns is a single-row SQLite table of free-text fields plus a phone-call list.

Time entries, expenses and mileage don't exist in any form. "Hours by Project" is a read-only rollup of ClickUp time entries — it displays hours, it cannot record them.

So this is not "add three forms". It is introducing a relational datastore, write paths with validation, and CRUD surfaces, into an app that has never written a domain record. The good news is that Recoup has already solved the modelling twice, and both solutions agree — and Phase 00 found it solved a third time, live, in mission-control, which is both a field source and the holder of the real data any consolidation must import.

03 The conflict, and how it was settled

Settled — dashboard wins

You already have two systems that each claim to own "Client" and "Project", and they disagree about what those words mean.

In ClickUp — which the dashboard reads today — a Client is a task in list 901112740853 with a status like "Won", and a Project is a task in another list. In Recoup, a Client is a business record with an hourly rate, contact details and archive state, and a Project belongs to one, carries a rate override and a lifecycle status.

Consolidating "three half-built dashboards" cannot mean holding both. Decision: the dashboard owns Client and Project. Rates, contacts and archive state have no natural home in a ClickUp task, and a two-way sync is a permanent tax on a single-user tool. ClickUp keeps tasks only.

04 Target data model

Taken from amb-recoup-web/supabase/migrations/001_initial_schema.sql and confirmed against the SwiftData models in amb-recoup. Translated to SQLite, multi-tenancy stripped (single user).

Because a Supabase sync is planned later, the schema is built so that sync is a mapping, not a rewrite: UUID primary keys rather than rowids, updated_at on every table, soft deletes via is_archived, and column names identical to Recoup's. organization_id is dropped and reintroduced as a constant at sync time.

-- Clients
CREATE TABLE clients (
  id TEXT PRIMARY KEY, name TEXT NOT NULL,
  hourly_rate REAL,                 -- nullable; feeds rate resolution
  contact_name TEXT DEFAULT '', contact_email TEXT DEFAULT '',
  contact_phone TEXT DEFAULT '', notes TEXT DEFAULT '',
  is_archived INTEGER DEFAULT 0, created_at TEXT NOT NULL);

-- Projects
CREATE TABLE projects (
  id TEXT PRIMARY KEY, client_id TEXT REFERENCES clients(id),
  name TEXT NOT NULL,
  hourly_rate_override REAL,        -- beats the client rate
  status TEXT DEFAULT 'active',     -- active | on_hold | completed
  notes TEXT DEFAULT '',
  is_archived INTEGER DEFAULT 0, created_at TEXT NOT NULL,
  urgent INTEGER DEFAULT 0,         -- NEW: Eisenhower axis
  important INTEGER DEFAULT 0);     -- NEW: Eisenhower axis

-- Time entries
CREATE TABLE time_entries (
  id TEXT PRIMARY KEY, client_id TEXT, project_id TEXT,
  date TEXT NOT NULL, hours REAL DEFAULT 0,
  rate REAL DEFAULT 0,              -- resolved at save, then frozen
  billable INTEGER DEFAULT 1, details TEXT DEFAULT '',
  created_at TEXT NOT NULL);

-- Expenses
CREATE TABLE expenses (
  id TEXT PRIMARY KEY, client_id TEXT, project_id TEXT,
  date TEXT NOT NULL, amount REAL DEFAULT 0,
  category TEXT DEFAULT 'other',    -- software|meals|travel|advertising|
                                    -- office|contractors|other
  vendor TEXT DEFAULT '', details TEXT DEFAULT '',
  billable INTEGER DEFAULT 0,
  recurring TEXT DEFAULT 'none',    -- none|weekly|monthly|yearly
  receipt_url TEXT, created_at TEXT NOT NULL);

-- Mileage
CREATE TABLE mileage_entries (
  id TEXT PRIMARY KEY, client_id TEXT, project_id TEXT,
  date TEXT NOT NULL, start_address TEXT DEFAULT '',
  end_address TEXT DEFAULT '', purpose TEXT DEFAULT '',
  miles REAL DEFAULT 0, round_trip INTEGER DEFAULT 0,
  total_miles REAL DEFAULT 0,       -- miles x2 when round_trip
  billable INTEGER DEFAULT 0, created_at TEXT NOT NULL);

-- Settings (mileage reimbursement rate)
CREATE TABLE settings (key TEXT PRIMARY KEY, value TEXT NOT NULL);
-- seed: mileage_rate = 0.67

Three business rules to carry over verbatim

  • Rate resolution. project.hourly_rate_override → client.hourly_rate → 0. Recoup's RateResolver.swift notes it is "resolved once at save and locked on the entry; never recomputed" — so editing a client's rate must not silently restate historical invoices. Copy that behaviour exactly.
  • Mileage total. total_miles = round_trip ? miles × 2 : miles, computed on write, stored. Reimbursement uses the org mileage rate, default 0.67.
  • Expense annualization. weekly ×52, monthly ×12, yearly ×1, none → null. Both Recoup apps expose this as a computed property; it drives recurring-cost reporting.

Also worth lifting: both apps prefill new entries from recent history — last-used client/project on a time entry, last category on an expense, and a "recent trips" picker keyed on (start, end, round_trip, miles). That is a small amount of code and most of what makes daily entry tolerable.

06 Cross-cutting work

Access control — the stakes just changed

The dashboard currently ships open by default: with no OWNER_DASHBOARD_AUTH_TOKEN set, anyone who can reach the address reads and writes everything, and the header says so with an "Unprotected" chip. That was an acceptable trade for MRR and a phone list on a tailnet.

It is a different proposition once the same host holds client contact details, contract rates, and financial records. Setting the token should become a precondition of this work, not a later cleanup.

Storage and migrations

The app uses node:sqlite with a single-row state table and one ad-hoc ALTER TABLE migration. Five related tables with foreign keys and a growing shape need a real migration runner — ordered, versioned, recorded in a schema_migrations table. Retrofitting that later is far more painful than starting with it.

The database also lives at cwd()/data/dashboard.sqlite with no backup story. Client financial records deserve better than "whatever is in the working directory of the process". Add a scheduled dump at minimum.

Routing

The app is one page of draggable widgets. Clients, projects and three entry types need list and form surfaces — that is real routing (/clients, /projects/[id], /time, …) with the dashboard becoming the index rather than the whole app. Recoup-web's template structure is a usable map.

Machine coupling

Live data resolves only on the one host: the ClickUp key comes from ~/.openclaw/secrets.json and the calendar shells out to ~/.local/bin/gog. Both are absolute paths under $HOME. That is survivable for a read-only dashboard and a poor foundation for a system of record. Worth fixing while the surface is small.

08 Decisions taken

D1 Dashboard owns Client and Project

Migrate off ClickUp for these two nouns. ClickUp keeps tasks only.

D2 Local SQLite now, sync to Supabase later

I advised against two writable stores and the risk stands — sync is the expensive part and rarely gets finished. Since it is the chosen path, the schema in §04 is built so the later sync is a mapping, not a rewrite: UUID keys, updated_at everywhere, soft deletes, and column parity with Recoup. Skipping those is what would turn the sync into a rewrite.

D3 Eisenhower replaces P0–P3 for projects

Store urgent and important on the project, derive the quadrant, retire the P0–P3 project widget. P0–P3 stays only where it belongs — on ClickUp tasks in Up Next.

D4 Tasks stay in ClickUp

Up Next and the /api/tasks/{id} status write-back are unchanged.

Phase 00 note: this was settled before mission-control could be read. It turns out MC's flagship module is a full kanban with its own tasks table, and the dormant auto-scheduler carries a third. The live database, profiled — 2026-08-13

Alex delivered a copy of the live AMB-mission-control.db (1.6 MB, integrity_check: ok, 48 tables — the live schema has drifted well past the repo's migration files, which is why profiling the real file mattered). Two findings sharpen phases 2–4:

  • Mission-control is dormant, not in daily use. Last time entry 2026-03-19, last expense 2026-03-16, last client edit 2026-03-16, last task touch 2026-04-15 — quiet for ~5 months. That further de-risks D5's absorb-and-retire, and mostly dissolves the D4 tension: MC's kanban stopped in April while the dashboard reads ClickUp live today. Its 92 open tasks are a one-time review/export, not a migration.
  • The import is small; the cleaning rules are the real work. clients 14 · projects 23 · time entries 98 · expenses 708 (2024-02 → 2026-03) · mileage 4 · recurring-expense definitions 13 · CoA 30 + category→account map 24. Under ~1,500 rows in total.

Cleaning rules the import must carry: client statuses need normalising (On Hold / on hold / prospect — note prospect is a pipeline state the client status set must include); one time entry has 10:30 as its date; one mileage row's total_miles disagrees with its round-trip flag; 84 expense rows carry a Revenue category inside the expenses table and need a human call at import time; categories are 11 free-text values, not the 7-value enum. Live-schema confirmations: mileage does have is_round_trip/total_miles (matching Recoup after all); time entries are all duration_hours with only 13 carrying start/end (D7's shape confirmed); expenses.account_code was never populated — the category→CoA link lives in category_account_map, so D6's "carry codes" imports that mapping rather than per-row codes; recurring is a separate recurring_expenses table (13 definitions, 25 generated rows linked), richer than the flag-on-the-row the plan drafted.

One number to not trust: summing MC's client MRR fields gives $3,350 active — the dashboard's hand-typed MRR says $42,500. The client rows were never kept current, so after the import the derived-MRR feature (§05) must not silently replace the typed figure until the client records are brought up to date.

D5 · SETTLED Absorb mission-control, or re-point at it?

The plan assumed the dashboard builds CRUD because nothing exists. Mission-control exists, works, and is live. Two coherent paths: (a) absorb — build in the dashboard per this plan, one-time import of MC's live rows (clients, projects, time, mileage, expenses, settings), retire MC; or (b) re-point — keep MC as the system of record and have the dashboard read/write its API, building no CRUD here.

Settled — absorb Build in the dashboard per this plan, one-time import of MC's live rows, retire mission-control. The dashboard exists because MC was too heavy — its own README says so — and re-pointing would leave two apps alive forever, which is how the count got to three dashboards in the first place.

D6 · SETTLED Accounting: carry or cut?

MC has working double-entry accounting — chart of accounts mapped to Schedule C lines, journal entries, Trial Balance / P&L / Balance Sheet. §04 has a flat 7-value category enum. Porting expenses without account_code and the CoA kills those reports and makes the import lossy.

Settled — carry codes, defer reports Keep account_code (plus company, is_reimbursable, recurring_day) on the dashboard's expenses table and import the CoA as reference data, so nothing is lost. Journal posting and the report screens wait for a later phase.

D7 · SETTLED Time entry shape: hours or start/end?

Recoup logs date + hours. MC logs start_time / end_time (plus a task link) and derives duration. The form you use daily should decide this, not the schema.

Settled — hours, nullable start/end Hours-only entry for speed, with nullable start_time/end_time columns so MC's rows import losslessly and a timer can be added later without a migration. MC's task links flatten into the details text on import.
